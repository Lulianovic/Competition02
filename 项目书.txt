# 慧灌智控（HuiGuan Smart Irrigation）

> 面向设施农业的多源感知、可信诊断与自适应节水控制系统  
> 基于 STM32F407ZG 的智能农业监测与灌溉控制项目

## 1. 项目简介

### 1.1 项目背景

在设施农业中，作物生长环境会受到土壤含水量、空气温湿度、光照强度等多种因素影响。传统灌溉方式通常依赖人工经验或固定阈值控制，难以根据环境变化及时调整灌溉策略，也缺乏对传感器异常、通信中断及执行设备运行时间的有效管理。

针对上述问题，本项目计划设计并实现一套基于 STM32F407ZG 微控制器的智能农业监测与灌溉控制系统。系统通过采集多种环境参数，结合数据有效性检查、灌溉需求评估和状态机控制，实现环境监测、自动灌溉、异常保护及运行记录等功能。

项目以仿真平台为主要开发与验证环境，在有限的开发周期内完成从传感器数据输入到控制指令输出的完整闭环，并通过对照实验验证控制策略的有效性。

### 1.2 项目目标

本项目不仅要实现基本的自动灌溉功能，还希望围绕控制可靠性和策略优化形成具有一定创新性的技术方案。

主要目标如下：

1. **多源环境监测：** 采集土壤湿度、空气温湿度和光照强度等环境数据，为灌溉决策提供依据。
2. **数据可信诊断：** 对传感器数据进行范围检查、有效性判断和超时检测，识别异常输入并采取保护措施。
3. **智能灌溉决策：** 以土壤湿度作为主要控制依据，结合其他环境参数构建灌溉需求评分机制。
4. **安全闭环控制：** 通过状态机管理水泵启停、最长运行时间、冷却间隔和故障状态，减少误动作与频繁启停。
5. **人机交互与运行记录：** 通过 OLED 显示屏（V1 不接 TFT）和串口终端展示环境数据、运行状态和决策原因。
6. **对照测试与效果评估：** 将多参数决策策略与固定阈值策略进行对比，评估其在控制稳定性、故障处理和模拟用水量等方面的表现。

### 1.3 项目定位

本项目定位为一套面向设施农业场景的嵌入式智能灌溉控制原型系统。

当前阶段以仿真验证为主，重点验证控制算法、软件架构和异常处理机制，不直接将仿真结果等同于真实农田的节水效果。若后续具备实际传感器和灌溉设备，可进一步开展实物测试。

## 2. 项目特色与创新思路

本项目的重点不是简单地将多个传感器连接到单片机，而是尝试建立一套具有数据判断、策略决策、执行保护和结果评估能力的完整系统。

### 2.1 多源环境感知

系统综合采集土壤湿度、空气温度、空气湿度和光照强度等数据。

其中，土壤湿度是灌溉控制的主要依据，空气温湿度和光照强度作为辅助判断因素，用于调整灌溉需求评分。辅助参数不能覆盖土壤湿度的安全约束，避免在土壤已经足够湿润时，仅因为其他环境因素变化而启动灌溉。

### 2.2 传感器可信诊断

系统不仅处理传感器数据，还需要判断数据是否可信。

计划实现以下功能：

- 数据范围检查：识别超出合理输入范围的数据。
- 数据有效性标记：区分正常数据、无效数据和暂时缺失的数据。
- 通信超时检测：判断传感器数据是否长时间没有更新。
- 异常状态保护：关键传感器数据无效时，禁止自动灌溉。
- 恢复确认机制：传感器恢复后，需要满足连续有效采样等条件，才能退出故障状态。

这一设计使系统能够在异常情况下优先保证控制安全，而不是盲目执行灌溉命令。

### 2.3 基于状态机的灌溉控制

采用有限状态机管理灌溉流程，将控制过程划分为待机、灌溉、冷却和故障等状态。

相比直接在主循环中反复判断多个条件，状态机能够明确各状态之间的转换条件，降低程序逻辑混乱、频繁启停和故障恢复不明确等问题。

### 2.4 多参数需求评分与策略对照

在固定阈值控制的基础上，进一步构建多参数灌溉需求评分模型。

系统首先判断土壤湿度是否满足灌溉的基本条件，再根据其他环境参数计算辅助需求评分。通过调整评分权重与控制参数，探索多源环境信息对灌溉决策的影响。

项目将保留固定阈值控制作为基准方案，在相同测试输入下比较两种策略的运行结果，避免仅凭主观判断认定新策略更优。

### 2.5 可复现的仿真实验

通过串口输入模拟传感器数据，能够在不完全依赖仿真平台内置传感器模型的情况下，测试不同环境变化和故障情景。

系统将记录环境数据、控制状态、故障代码和决策原因，便于复现测试过程并形成竞赛报告中的实验数据。

> 以上属于项目拟实现的设计特色。最终能否形成有效创新，需要结合实现结果、对照实验和已有方案进行验证，不预先宣称具有未经验证的节水效果。

## 3. 系统总体架构

### 3.1 系统工作流程

```text
环境数据输入
    │
    ├── 土壤湿度
    ├── 空气温湿度
    └── 光照强度
    │
    ▼
数据采集与格式转换
    │
    ▼
数据有效性检查
    │
    ├── 数据正常
    │      │
    │      ▼
    │   灌溉需求评估
    │      │
    │      ▼
    │   状态机控制
    │      │
    │      ▼
    │   水泵控制与运行保护
    │
    └── 数据异常
           │
           ▼
       故障处理与安全保护

以上各环节的运行状态
    │
    ▼
OLED 显示、串口调试与数据记录
```

### 3.2 软件分层设计

系统采用模块化设计，将底层硬件访问、数据处理、决策控制和界面显示分开。

| 软件层 | 主要职责 |
|---|---|
| 硬件驱动层 | ADC、GPIO、UART、I²C/SPI、定时器等外设访问 |
| 数据采集层 | 获取传感器数据，完成原始值转换与更新 |
| 数据诊断层 | 数据范围检查、有效性判断、超时与异常检测 |
| 决策控制层 | 计算灌溉需求、执行状态机和安全约束 |
| 执行器控制层 | 管理水泵、继电器及后续扩展设备 |
| 交互与记录层 | 显示运行状态、串口调试、记录实验数据 |

各模块通过明确的接口交换数据，减少不同功能之间的耦合，方便后续更换传感器型号或调整控制算法。

## 4. 硬件与开发环境

### 4.1 核心控制器与开发环境（已按实际工程修订）

**说明：平台课程资源名中的"（开源鸿蒙）"是课程系列标识。平台下发的工程本身是裸机 C 工程，内部不含 OpenHarmony / LiteOS / CMSIS-OS 代码，也不涉及 ArkTS / JS 应用层开发；因此本项目按标准嵌入式 C 编写。**

- 主控芯片：STM32F407ZG（LQFP144）
- 开发平台：开源鸿蒙嵌入式虚拟仿真平台
- 编译工具链：`arm-none-eabi-gcc` + Makefile（`-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard`，`-Og`，`-u _printf_float`）
- 软件框架：**STM32 标准外设库 StdPeriph V3.5.0**（非 HAL，不使用 CubeMX 生成外设代码）
- 运行方式：裸机非阻塞主循环 + 定时调度
- 时钟：HSE 8 MHz，PLL_M = 8 / PLL_N = 336 / PLL_P = 2，系统主频 **168 MHz**
- 基础工程：`code/base_code_STM32F407`（CORE / HARDWARE / SYSTEM / USER / STM32F4xx_FWLib + Makefile + 启动文件 + 链接脚本）

项目不引入 RTOS，优先完成核心功能和闭环控制，待系统稳定后再考虑 DMA、中断优化或其他扩展。

### 4.2 实际接入的传感器与执行设备（V1 已冻结）

V1 只接入下表器件，表中之外的传感器一律不接：

| 类别 | 实际器件 | 平台元件库名 | 接口 / 引脚 | 用途 |
|---|---|---|---|---|
| 土壤监测 | YL-69 土壤湿度模块 | 土壤湿度传感器 YL-69 | AO → PA0（ADC1_IN0） | 灌溉主控制依据 |
| 空气环境 | DHT11 温湿度模块 | 温湿度传感器（BK_DHT11） | DATA → PB0（单总线） | 辅助判断 |
| 光照监测 | BH1750 | 光照度传感器（BK_BH1750） | SCL → PB8 / SDA → PB9 | 辅助判断 |
| 备用模拟量 | 可调电压源 1.65 V | 可调电压源 | + → PA1（ADC1_IN1） | 备用通道 / 标定 |
| 执行设备 | 继电器模块 + 水泵 | 继电器（BK_Relay）+ 水泵 | DQ → PC0，COM → +5V，NO → 泵 + | 灌溉执行 |
| 报警提示 | 有源蜂鸣器 | 有源蜂鸣器 | + → PC1，− → GND | 故障报警 |
| 状态指示 | LED + 330Ω 限流电阻 | LED + 电阻 | PC2 → 330Ω → LED → GND | 运行状态 |
| 人机交互 | OLED 128×64（I²C） | OLED 显示屏（I2C 128*64） | SCL → PB8 / SDA → PB9（与 BH1750 共总线） | 数据显示 |
| 调试通信 | 串口终端助手 | 串口终端助手 | PA9 / PA10（USART1，115200-8-N-1） | 调试与数据注入 |

**明确不接入（列为后续扩展）：** RS485 系列变送器（SN_3000_TR、SN_3001_YM 等）、CO₂、NPK、EC、pH 传感器、WiFi / ESP8266、TFT 显示屏、步进电机与舵机。

**电源约定：** `+3V3` 供全部传感器与 OLED，`+5V` 仅供继电器线圈与水泵；两路电源只在 GND 共地，全图只有一个 GND 网络。

**YL-69 的 DO 脚悬空**，只使用 AO 模拟输出；BH1750 的 ADDR 接地后地址为 `0x23`；OLED 地址为 `0x3C`。

**YL-69 供电与仿真参数：** 该模块标称供电范围 **3.0～5.0 V**，本项目统一取 **3.3 V**。原因：3.3 V 供电时 AO 的满量程即为 3.3 V，与 STM32 的 ADC 参考电压一致，既不会超出 ADC 输入范围，也在 IO 耐压之内（若用 5 V 供电，AO 可能超过 3.3 V，会打满 ADC 甚至损伤引脚）。仿真模型提供"土壤湿度"参数（单位 %，当前值 40），运行中可随时调整以构造测试场景；板载电位器只影响 DO 的翻转阈值，本项目不接 DO，因此无需调整。

**接口数量说明（按仿真平台实际模型）：**

- 水泵模型**只有一个电气接口**，其另一端在模型内部已接地，因此只需 `NO → 水泵接口` 一根线，**不需要、也没有第二根线接回 GND**。
- 可调电压源同样只有一个接口，其内部已以公共地为参考。
- 继电器模块为成品模块（带 DQ 控制脚与板上三极管、续流二极管），**MCU 可直接驱动 DQ**，不需要外加三极管驱动电路。

### 4.3 仿真平台适配原则

由于不同仿真平台支持的 STM32 外设、传感器模型和屏幕接口存在差异，硬件连接采用以下原则：

1. 优先使用平台已有的真实器件模型。
2. 对没有现成模型的模拟量传感器，可使用可调电压源配合 ADC 验证数据处理逻辑。
3. 对没有模型的串口或 RS485 传感器，可使用串口数据注入模拟其输出。
4. 对尚未接入真实屏幕的版本，先通过串口终端显示数据。
5. 对继电器、水泵等执行设备，应确认模型的有效电平和反馈能力，不能默认所有继电器都是高电平有效。

采用模拟数据的模块需要在文档和演示中明确标注，不能将软件模拟输入描述为真实传感器的实测结果。

### 4.4 最终引脚分配（已随接线冻结）

下表为原理图接线完成后的最终分配，后续代码与外设配置均以此为准，不得随意改动：

| 功能 | 引脚 | 外设 / 模式 | 网络名 |
|---|---|---|---|
| 土壤湿度模拟输入 | PA0 | ADC1_IN0 | `SOIL_AO` |
| 备用模拟输入 | PA1 | ADC1_IN1 | `SPARE_AI` |
| 空气温湿度数据 | PB0 | GPIO 单总线（输入/输出切换） | `DHT_DATA` |
| I²C 时钟 | PB8 | I2C1_SCL | `I2C1_SCL` |
| I²C 数据 | PB9 | I2C1_SDA | `I2C1_SDA` |
| 串口发送 | PA9 | USART1_TX | `UART1_TX` |
| 串口接收 | PA10 | USART1_RX | `UART1_RX` |
| 继电器（水泵） | PC0 | GPIO 推挽输出 | `RELAY_IN` |
| 蜂鸣器 | PC1 | GPIO 推挽输出 | `BUZ` |
| 状态指示灯 | PC2 | GPIO 推挽输出 | `LED_ST` |

补充说明：

- 串口参数：115200、8-N-1。
- I²C 总线挂两个从机：BH1750（ADDR 接地，地址 `0x23`）与 OLED（地址 `0x3C`）。
- 继电器为模块版（带 DQ 控制脚与板上三极管驱动），**有效电平需实测确认**，代码中用宏配置，便于一键切换。
- 上述 10 个引脚为冻结引脚，占用即冲突；修改引脚必须同步修改代码。
- 平台基础工程中原有驱动的引脚与本表不一致的部分，必须调整到本表，详见 5.1。

**+5V 独立供电与共地（已按最终接线确认）：**

- 5V 直流电压源（电池）正极 → 继电器 `VCC` 与 `COM`；负极 → 继电器 `GND`，并**必须接到 GND 符号**。
- **电池负极在未接到 GND 之前是悬空端子，并不等同于“地”**。只有接到 GND 符号后，它才与芯片的地成为同一个参考节点。
- 不共地的两个后果：① 水泵的电流回路被断开（水泵模型内部返回端接平台地，电流无法回到电池负极），水泵不会转；② PC0 的控制信号以芯片地为参考，与继电器所参考的电池负极不是同一节点，信号无回流路径，继电器不会吸合。
- 独立供电 ≠ 独立地：+3V3 与 +5V 两路**正极彼此独立**，只在 GND 处共地，不存在电源短路。

**驱动改造说明（必须做，否则与接线不符）：**

- `led.c` 实际初始化的是 PA0，与 DHT11 的数据脚冲突；状态灯已改到 **PC2**，需同步修改 LED 驱动与 `LED` 宏（原宏写成 PF9，与实现也不一致）。
- `iic_oled.c` 的软件 I²C 使用 PB6/PB7，与基础工程中硬件 I2C1（`bsp_i2c_ee.c`，AT24C02 用）完全同脚；本项目不用 EEPROM，统一改到 **PB8/PB9**，并且不要同时初始化两套 I²C。
- `dht11.h` 的 `DHT11_DQ_OUT/IN` 宏指向 PA0，需改为 **PB0**。
- `adc.c` 目前只初始化 PA1 / ADC_Channel_1，需扩展为 **PA0（通道 0）+ PA1（通道 1）** 双通道采集。

### 5.2 数据结构

系统使用统一的数据结构保存环境数据、有效性标志和更新时间。

```c
typedef struct {
    /* 工程单位值 */
    float soil_moisture_pct;   /* 0~100 %，由 ADC 原始值换算 */
    float air_temperature_c;   /* ℃，DHT11 返回 0.1℃ 整数，除以 10 */
    float air_humidity_pct;    /* %RH，DHT11 返回 0.1%RH 整数，除以 10 */
    float light_lux;           /* lux，BH1750 直接输出 */

    /* 原始值，便于标定与日志追溯 */
    uint16_t soil_adc_raw;     /* 0~4095，12 位 ADC */
    uint16_t spare_adc_raw;    /* PA1 备用通道 */

    /* 有效性标志 */
    uint8_t soil_valid;
    uint8_t air_valid;
    uint8_t light_valid;

    /* 各自更新时间（ms，来自系统节拍） */
    uint32_t soil_update_ms;
    uint32_t air_update_ms;
    uint32_t light_update_ms;
} AgriData;
```

其中：

- `soil_moisture_pct`：土壤湿度百分比（0~100 %），由 ADC 原始值换算。
- `air_temperature_c` / `air_humidity_pct`：空气温度（℃）与相对湿度（%RH）。
- `light_lux`：光照强度（lux）。
- `soil_adc_raw` / `spare_adc_raw`：12 位 ADC 原始值（0~4095），用于标定与回溯。
- `*_valid`：对应数据是否通过有效性检查。
- `*_update_ms`：各自的数据更新时间，用于超时判断。

注意：ADC 的 0～4095 只是 12 位原始数字量，**不能直接当作土壤湿度百分比**；DHT11 驱动返回的是 0.1℃ / 0.1%RH 的整数，需要除以 10。转换关系应集中在采集层（`sensor_port.c`）完成，上层只使用工程单位值。

### 5.3 模块接口规划

| 模块 | 主要接口 | 作用 |
|---|---|---|
| 数据采集 | `SensorPort_Init()` | 初始化采集模块 |
| 数据采集 | `SensorPort_Process()` | 更新传感器数据 |
| 数据采集 | `SensorPort_GetData()` | 获取当前环境数据 |
| 控制算法 | `Control_Init()` | 初始化控制状态 |
| 控制算法 | `Control_Process()` | 执行决策和状态转换 |
| 控制算法 | `Control_GetState()` | 获取当前控制状态 |
| 控制算法 | `Control_GetReason()` | 获取决策原因 |
| 水泵控制 | `Pump_SetState()` | 设置水泵控制输出 |
| 串口协议 | `SerialProtocol_Process()` | 解析并处理接收数据 |
| 数据记录 | `Log_Write()` | 输出或保存运行记录 |

函数签名可根据实际实现调整，但应尽量保持模块职责清晰。数据采集模块不应直接决定水泵启停，控制模块也不应依赖特定显示屏驱动。

## 6. 核心控制策略

### 6.1 固定阈值基准策略

第一阶段先实现固定阈值控制，确保系统能够完成稳定、可预测的自动灌溉闭环。

初始仿真参数可以设置为：

| 参数 | 示例值 | 用途 |
|---|---:|---|
| 灌溉启动阈值 | 30% | 土壤湿度低于该值时，可申请启动灌溉 |
| 灌溉停止阈值 | 40% | 土壤湿度达到该值时，停止灌溉 |
| 最长连续运行时间 | 10 秒 | 防止水泵持续运行 |
| 灌溉冷却间隔 | 5 秒 | 避免短时间内频繁启停 |
| 数据超时时间 | 3 秒 | 识别长期未更新的数据 |

以上参数仅用于软件仿真和控制逻辑测试，不代表任何特定作物的推荐农艺参数。真实使用时需要结合传感器标定、作物需求、土壤类型和灌溉设备进行调整。

**仿真操作建议（配合 YL-69 的"土壤湿度"参数）：**

| 设置的土壤湿度 | 预期系统行为 | 验证目的 |
|---|---|---|
| 20 %（< 启动阈值 30 %） | 允许启动灌溉，水泵开启 | T02 启动条件 |
| 55 %（> 停止阈值 40 %） | 正在灌溉时停泵，进入冷却 | T01 停止条件 |
| 35 %（滞回区间内） | 保持当前状态，不频繁切换 | T03 滞回与稳定性 |
| 超出 0～100 或数据长期不更新 | 标记无效 / 触发超时保护 | T04、T05 异常保护 |

采用启动阈值与停止阈值分离的方式，可以形成一定的滞回区间，减少土壤湿度在临界值附近波动时产生的频繁启停。

### 6.2 状态机设计

计划使用以下四种主要状态：

| 状态 | 含义 | 主要行为 |
|---|---|---|
| `IDLE` | 待机 | 水泵关闭，持续监测环境数据 |
| `IRRIGATING` | 灌溉中 | 水泵开启，检查停止条件和运行时长 |
| `COOLDOWN` | 冷却中 | 水泵关闭，等待下一次灌溉许可 |
| `FAULT` | 故障 | 进入安全状态，禁止自动启动水泵 |

状态转换的基本原则：

1. 关键传感器数据无效或超时时，进入安全保护流程。
2. 满足启动条件且所有保护条件通过后，才允许开始灌溉。
3. 达到停止阈值或最长运行时间后，关闭水泵。
4. 灌溉结束后进入冷却状态，避免频繁启停。
5. 故障状态下不允许无限自动重试；恢复前需要满足明确的故障解除条件。
6. 系统上电和复位后，水泵控制输出应处于关闭状态，并重新检查数据有效性。

实际程序应明确不同状态下的条件优先级，避免同一轮调度中出现互相矛盾的控制指令。

### 6.3 多参数灌溉需求评分

在基准策略稳定后，引入多参数需求评分机制。

设：

- \(M\)：根据土壤湿度计算的归一化灌溉需求；
- \(T\)：根据空气温度计算的辅助需求；
- \(H\)：根据空气湿度计算的辅助需求；
- \(L\)：根据光照强度计算的辅助需求。

可构建以下评分模型：

\[
S=w_M M+w_T T+w_H H+w_L L
\]

其中：

\[
w_M+w_T+w_H+w_L=1
\]

各参数应转换到统一的评分范围，权重和评分函数根据项目假设及实验方案确定。

控制逻辑采用两级判断：

**第一级：安全约束。** 检查土壤湿度、数据有效性、运行时长和冷却状态等条件，决定是否允许灌溉。

**第二级：需求评估。** 在满足安全约束的前提下，根据综合评分决定是否启动灌溉或调整决策阈值。

土壤湿度应保留主要控制地位。空气温湿度和光照不能绕过土壤湿度约束，也不能在关键数据缺失时直接生成自动灌溉指令。

由于多参数评分本身并不必然优于固定阈值控制，项目将通过同一组输入场景开展对照实验，评估其是否减少不必要的灌溉动作或改善控制稳定性。

### 6.4 故障处理机制

| 异常情况 | 处理方式 |
|---|---|
| 土壤湿度超出有效范围 | 标记数据无效，禁止自动灌溉 |
| 关键传感器超时 | 进入安全保护流程 |
| 串口数据格式错误 | 拒绝该条输入并记录错误 |
| 水泵运行超时 | 关闭水泵，记录故障原因 |
| 传感器数据恢复 | 连续有效采样后按恢复规则处理 |
| 系统复位 | 默认关闭水泵，重新验证数据 |

如果仿真平台无法提供水泵实际运行反馈，则只能确认程序已发出控制命令，不能直接宣称水泵已经实际出水。若后续加入流量计或其他反馈装置，才能进一步判断执行器是否按预期工作。

## 7. 串口调试与模拟数据输入

### 7.1 设计目的

由于部分传感器可能没有对应的仿真模型，系统计划使用 UART 串口作为调试和测试入口。

通过串口终端输入模拟数据，可以主动构造不同环境条件，快速验证控制算法和异常处理逻辑。

### 7.2 数据协议

建议采用简单的文本协议，每条命令以换行符结束。

| 命令示例 | 含义 |
|---|---|
| `SOIL,25.0` | 设置模拟土壤湿度 |
| `AIR,28.0,60.0` | 设置模拟空气温度和湿度 |
| `LIGHT,18000` | 设置模拟光照强度 |
| `MODE,AUTO` | 请求切换到自动模式（默认模式，只使用真实传感器数据） |
| `MODE,TEST` | 进入测试模式，此时才允许串口注入模拟数据 |
| `MODE,SCORE` | 切换到多参数需求评分策略（默认 `MODE,THRESHOLD` 为固定阈值） |
| `FAULT,SOIL_TIMEOUT` | 在测试模式中模拟土壤数据超时 |

以上数据均为测试输入示例，不代表真实测量结果。

**模式约束（已确定为“仅测试模式生效”方案）：** 默认 `MODE,AUTO` 下只使用真实传感器数据；串口注入命令（`SOIL` / `AIR` / `LIGHT`）必须先执行 `MODE,TEST` 才生效，退出测试模式后自动恢复传感器输入。这样既能人为构造干旱、故障等测试场景，又能保证演示与答辩时使用的数据全部来自真实传感器模型。

### 7.3 协议处理要求

- 使用固定长度接收缓冲区，防止输入过长导致越界。
- 接收中断中仅完成轻量级数据搬运和状态标记。
- 在主循环中进行完整的字符串解析、范围检查和命令处理。
- 对格式错误、未知命令和超范围数据进行拒绝处理。
- 测试故障命令应仅在测试模式下开放，不能让任意串口输入直接控制水泵。
- 模拟数据与真实传感器数据应明确区分，防止测试数据污染实验结论。
- 日志中通过 `source` 字段（或等价字段）标注当前数据来自 `SENSOR` 还是 `SERIAL`，便于回溯与报告引用。

## 8. 程序调度与运行机制

### 8.1 主循环设计

系统采用非阻塞式主循环，尽量避免使用长时间的阻塞延时。

```text
系统初始化
    │
    ▼
主循环
    ├── 处理串口接收与命令
    ├── 更新传感器数据
    ├── 检查数据有效性与超时
    ├── 执行灌溉决策状态机
    ├── 更新水泵控制输出
    ├── 刷新显示界面
    └── 写入运行日志
    │
    └── 循环执行
```

### 8.2 初步调度周期

| 任务 | 建议周期 | 说明 |
|---|---:|---|
| 按键扫描 | 10～20 ms | 如需要实体按键 |
| ADC 采样 | 100 ms | 根据传感器响应调整 |
| 环境数据更新 | 500～1000 ms | 根据接口和传感器刷新频率调整 |
| 控制决策 | 500 ms | 检查灌溉条件与状态转换 |
| 显示刷新 | 200～500 ms | 避免过度刷新 |
| 数据日志 | 500～1000 ms | 根据测试需求调整 |
| 故障检查 | 100～500 ms | 及时处理关键异常 |

以上周期为初始设计值，实际调度需要结合传感器响应速度和仿真性能调整。

实现说明（按实际工程）：本工程使用 StdPeriph 标准库，**没有 `HAL_GetTick()`**。且 `delay_us()` / `delay_ms()` 内部会重配 SysTick 并在结束时关闭，**不能作为系统节拍使用**；因此调度基准采用 **TIM2 定时器计数**或自行维护的毫秒计数器，`delay_us()` 只用于 DHT11 等严格时序场合。中断服务函数中不应执行复杂的字符串解析、显示刷新或完整控制流程。

## 10. 测试与评估方案

### 10.1 功能测试用例

| 编号 | 测试场景 | 预期结果 |
|---|---|---|
| T01 | 土壤湿度高于停止阈值 | 水泵保持关闭 |
| T02 | 土壤湿度低于启动阈值且保护条件通过 | 允许启动灌溉 |
| T03 | 土壤湿度位于启动与停止阈值之间 | 保持符合当前状态机的状态，不频繁切换 |
| T04 | 土壤湿度输入超出有效范围 | 标记异常并禁止自动灌溉 |
| T05 | 关键传感器数据长时间未更新 | 触发超时保护 |
| T06 | 串口输入格式错误或数据超范围 | 拒绝异常输入 |
| T07 | 水泵运行超过最长允许时间 | 关闭水泵并记录故障 |
| T08 | 灌溉后土壤湿度没有立即变化 | 结合观察窗口判断，不立即认定设备故障 |
| T09 | 切换手动与自动模式 | 按预定模式规则处理，不能绕过安全约束 |
| T10 | 系统复位或重新上电 | 水泵默认关闭，重新验证数据 |
| T11 | 长时间连续运行 | 检查状态、日志和控制输出是否稳定 |
| T12 | 固定阈值与多参数策略对照 | 使用相同输入记录两种策略的结果 |

### 10.2 对照实验设计

实验分为两个阶段。

**第一阶段：基础功能验证。**

验证传感器数据处理、状态机转换、保护机制、串口输入和运行日志是否正常。

**第二阶段：控制策略对照。**

使用相同的环境输入序列分别运行：

- 方案 A：固定阈值控制；
- 方案 B：多参数需求评分控制。

记录两种方案在相同场景中的控制行为，并分析其优缺点。

### 10.3 评价指标

| 指标 | 计算或评估方式 | 用途 |
|---|---|---|
| 模拟用水量 | 设定的流量参数 × 水泵累计运行时间 | 比较模型条件下的用水差异 |
| 灌溉启动次数 | 统计水泵启动事件 | 观察控制频率 |
| 环境目标偏离时间 | 统计湿度等指标超出设定目标区间的时间 | 观察控制效果 |
| 决策响应时间 | 从输入条件变化到控制状态变化的时间 | 评价响应速度 |
| 异常处理正确率 | 正确处理的异常用例数 ÷ 异常测试总数 | 评价故障处理能力 |
| 状态切换稳定性 | 统计临界区间内不必要的状态切换 | 观察控制是否抖动 |

如果仿真环境没有模拟土壤水分扩散、蒸发和作物蒸腾等过程，则模拟用水量只能反映设定流量与运行时间的关系，不能直接代表真实农田节水效果。

实验报告应保存原始输入、控制参数、测试日志和计算过程。只有在结果支持的情况下，才能得出某种策略更优的结论。

## 11. 一个月开发计划

项目周期约为 30 天。整体采取“先跑通闭环，再完善算法，最后集中验证和整理材料”的顺序。

| 时间 | 主要任务 | 阶段成果 |
|---|---|---|
| 第 1～3 天 | 确认仿真平台、芯片型号、时钟和外设配置；完成最小工程 | 工程能够编译运行，串口输出正常 |
| 第 4～7 天 | 完成 GPIO、ADC、UART 等基础外设测试；建立统一数据结构 | 能读取或模拟输入环境数据 |
| 第 8～12 天 | 完成数据有效性检查、状态机和水泵控制 | 实现基础自动灌溉闭环 |
| 第 13～16 天 | 增加多参数需求评分和安全约束 | 完成两种控制策略 |
| 第 17～21 天 | 编写测试用例、故障测试和对照实验程序 | 获得初步测试日志和分析结果 |
| 第 22～25 天 | 集成显示界面、完善日志和模块接口 | 形成完整系统演示版本 |
| 第 26～28 天 | 整理项目文档、实验报告、答辩 PPT 和演示流程 | 形成可展示的项目材料 |
| 第 29～30 天 | 修复关键问题、冻结版本、备份工程并进行最终演练 | 提交版本和最终演示材料 |

### 开发优先级

为了保证项目按时完成，采用以下优先级：

- **P0：必须完成。** 工程可运行、环境数据输入、基础控制、状态机、安全保护和基本测试。
- **P1：重点完善。** 多参数评分、对照实验、异常诊断、运行日志和可复现测试。
- **P2：有余力再做。** 完整 TFT 界面、更多传感器接入、Wi-Fi 上传、远程监控和高级算法。

如果某个传感器或屏幕驱动迟迟无法在仿真平台中运行，应优先采用串口模拟或其他可验证的输入方式，确保核心控制闭环按期完成。

## 12. 风险分析与应对措施

| 风险 | 可能影响 | 应对措施 |
|---|---|---|
| 仿真平台不支持某些传感器 | 无法直接采集数据 | 使用可调模拟量或串口注入验证软件逻辑 |
| 屏幕接口与预期不一致 | 显示驱动开发延误 | 先使用串口输出，确认型号后再接入屏幕 |
| ADC 原始值无法直接转换为湿度 | 数据失真 | 查阅传感器资料并进行标定；模拟数据明确标注 |
| RS485 通信调试困难 | 多源数据采集延期 | 先验证 UART 和协议处理，再单独调试 RS485 |
| 多参数算法无法证明更优 | 创新效果缺乏证据 | 设置基准方案和相同测试输入，按实验结果分析 |
| 控制状态切换不稳定 | 水泵频繁启停 | 使用滞回区间、冷却时间和最长运行时间 |
| 开发时间不足 | 项目无法完整交付 | 优先完成 P0 功能，减少非必要扩展 |

## 15. 后续扩展方向

在核心功能稳定后，可根据时间和仿真平台支持情况进行扩展：

- 接入更多土壤和作物环境传感器；

- 增加 Wi-Fi 通信和远程监测；
- 增加流量反馈，实现更完整的灌溉执行验证；
- 引入历史数据分析，优化需求评分参数；
- 在具备真实设备和试验条件后，开展实际节水效果验证。

这些扩展不应影响基础闭环控制、安全保护和对照测试的按期完成。

## 16. 项目总结

“慧灌智控”以 STM32F407ZG 为核心，围绕设施农业环境监测与自动灌溉需求，构建由多源数据采集、可信诊断、灌溉决策、状态机控制和运行记录组成的嵌入式系统。

项目的实施重点是先建立可靠的基础控制闭环，再逐步加入多参数评分、异常诊断和策略对照实验。通过模块化软件设计和可复现的仿真测试，形成一套能够运行、能够验证、能够解释控制原因，并具备后续扩展能力的智能灌溉原型系统。

本项目最终将以可运行的工程、完整的测试记录和有依据的实验分析作为主要成果，而不是仅停留在系统概念或算法设想层面。
